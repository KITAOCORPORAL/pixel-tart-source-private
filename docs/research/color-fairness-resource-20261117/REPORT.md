# 高光净收益与零RAW资源堵点 · 2026-11-17

**本轮回答：高光V1有特定的裁切前收益，但尚未证明新增工具的普遍净收益；legacy RAW后处理仍有可复现的全帧副本/重开峰值缺口。** 候选数学、产品源码、默认曝光/旧配方、发行DLL和锐化封存均未改；RAW/native解码0、无新重型账本。

## 1. 公平比较如何成立

先读实际顺序：BasicTone在同一节点内EOTF→自身曝光的亮度有理映射→brightness→highlights/shadows→contrast→whites/blacks→共同比例调整→EncodeGamut。Whites不是单独独立于该顺序的上游工具。Curve在编码sRGB，使用当前产品的主RGB形状保持Hermite曲线/LUT，R/G/B子曲线全恒等。RenderedSrgbExposure则是EOTF→EV→OETF→逐通道clip。

因此固定5组：post-highlights/post-whites/post-curve是原曝光裁切后补救；basic-highlights/basic-whites从同一未加曝光的编码输入出发，使用BasicTone自己的曝光/控制，不能冒充只改一个上游肩部的因果差。所有输出同为rendered-sRGB float，可比较最终图像，但来源/次序差异明示。

计划在有效计算前固定：6个原ROI×EV0/+1（4实拍ROI、2合成），不重选ROI；每类同曝光固定强度，高光/白场−50，曲线(0,0),(.25,.25),(.5,.5),(.75,.75),(1,.875)。中间调用原独立锚点0.03≤输入线性Y≤.35、每4行列、至少16像素；不是在被评价ROI里临时找锚点。进一步只匹配固定亮部掩码meanY，曝光/控制幅度在预注册范围内按固定grid/首个括区/固定二分求解，不做输出后归一化。不是全局搜索最漂亮图，也不增加Amount/Knee配置。

控制实际调用ColorStudioToolProcessor/RenderedSrgbExposure，源码与e818/433相关核blob相同；V1同曝光/中间调匹配直接读取1bf已有f32，没有新执行候选。最早近似Python执行器发现公式/域/锚点错误，已拒绝为NOT_VALID_EVIDENCE；随后修正执行绑定并重新冻结计划。它的72条数字不参与本结论。精确控制执行2轮，第二轮仅补充指标/记录，最终权威12,162请求、约104MiB私有峰值、512MiB守卫内exit0；没有借此重跑候选或RAW。工具失败和边界变更在RESEARCH_EXECUTION.json，未静默改ROI或选择规则。

## 2. 收益是否成立

180幅查看面板=12条件×5类×3种条件，不是180份独立照片/实验。60个方法条件中50个有固定中间调锚点，17个在预定范围同时匹配中间调与高亮；33个范围内无双匹配，10个Canon项因原锚点不足不可比。失败/不可比灰列保留。

双匹配门限：锚点绝对Y误差≤2e−5、完整384 ROI高亮meanY相对误差≤0.5%。所有17个匹配组完整ROI复核通过。q99/max白点同时报告但没有再拟合，不能说亮部形状/最大白点/颜色已经相同。例如暖纹理EV+1的V1/曲线最大Y约.9611/.7388，肩部EV0约.8750/.8288；所以纹理优势仍与白点/分布差异耦合，没有证明在中间调、亮部均值、白点三者同时匹配后仍成立。

皮肤/发丝EV0与EV+1的曲线双匹配均成立；V1相对曲线梯度小幅增加约2.5%–9.2%，但亮度/局部反差关系复杂，不能把数字直接变主观评分。原输入贴顶通道仍未恢复。合成两组清楚标记，不能当白衣/金属；Canon原锚点缺失仍不可比。

**判断：维持HL-A优先评审，暂不认为新增控制已值得接入。** 它在裁切前保留新曝光增量有可见优势；但现有BasicTone已有接近结果，在EV0有时反而更好。新控制的可预测性只得到数学/顺序解释，未做用户易用性实验；固定最大通道膝点也会让高饱和颜色先触发，EV0亮度代价仍存在。白衣、金属、脸部与多光照实拍缺项不变，本轮没有扩大图库。

## 3. 内存堵在哪里

详见专门的RESOURCE_FINDINGS.md与资源图（不再重复全部取证日志）。旧820b确认worker退出/导入完成后约199秒父进程2066.87MiB越限，旧具体分配根仍未知。本轮两个零RAW生产VM宿主补到可复现堵点：

- 完整100%预览保留约459.90MiB主float与约114.97MiB完整RGB24/WIC持有；中性legacy RAW导出仍Clone+Preset Copy两个fullfloat并生成导出不需要的完整显示adapter，峰值2430.46MiB触发守卫。
- 新进程重开、仅代理预览下TIFF实际导出完成，像素/16位/ICC与既存payload相同；导出后约1841.33MiB。Dispose自然空闲后同进程再次读缓存，2073.79MiB越限。Private不降单独不证明泄漏，但容量门已经失败。

Target与Editor共享master、source与fullDisplay共享Bitmap，均按对象id去重；磁盘cache不当额外RAM。e818/433既有修复未改这条legacy全帧分配链，不能借renderedTIFF成功升级它为通过。这两轮是受控资源FAIL，不是普通产品或新candidate验收。旧STOP/账本保留、无原RAF读取/RAWnativeworker、无forceGC、无新重型账本。

## 4. 最小后续建议与停点

- 先限定legacy RAW中性/点节点导出：避免为高精度导出生成整幅显示adapter；评估无副本只读borrow或有限工作缓冲。不能简单return master再让using output.Dispose释放编辑/撤销仍持有的输入。空间/tile节点需独立像素门禁，不自动扩成算法变更。
- 给全帧工作集和同进程重开明确准入/所有权/在途任务边界，按自然回收验证，不能依赖forceGC、清全局cache或删旧证据过关。加GraphScope并不自动降低OS提交，池保留也占预算。
- 高光继续以当前公平图由用户看肤亮代价/既有工具是否够用；不创建Amount/V2或实现HL-A。新增材料缺项精确列出，不能合成补位。
- XTrans适配与新cold/rebuild预算仍另决；本轮只是零RAW回放，旧三批STOP和余额未动。锐化V1封存；TIFF旧内存成果不包装成色彩算法进展。

成果推送后停在算法/产品修改前。最短入口HANDOFF.md；原失败/输出/图片/采样在本地原位置，照片不进Git。
