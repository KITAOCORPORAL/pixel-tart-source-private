# Pixel Tart UI Design System

状态：Design Constitution v1.0  
建立日期：2026-09-10  
适用范围：Pixel Tart 全部桌面端界面、模块工作区、浮层、菜单、任务与状态反馈  
优先级：本文件及同目录 `02`—`07` 是后续 UI / UX 设计与实现的唯一规范；旧规范仅作为迁移依据，不再用于新增设计决策。

## 00 当前 UI 审查

### 0.1 审查边界

本次审查基于活动工作树 `feature/asset-library-eagle-shell-context-p36`，检查了：

- 应用壳层、页面可见性与导航结构；
- `Resources/DesignSystem` 下主题、颜色、字号、间距、圆角与控件资源；
- 工作台、工作日历、素材库、在线选片、联机拍摄、项目历史、摄影收支、设置及已有弹窗；
- 素材库自动验收与模块 UI 截图；
- Popup、ContextMenu、Dialog、Toast、Loading、Empty 与任务状态实现；
- 已有产品、架构、验收和设计文档。

灵感托盘目前是素材库内的持久化抽屉能力；情绪板与策划中心尚无完整 UI；独立大图 Viewer 尚未实现。因此相关章节定义未来标准，不把规划能力描述为当前成品。

### 0.2 已有基础

当前仓库并非没有设计系统。已有 Dark / Light / High Contrast 主题、语义颜色、Typography、4px 间距序列、圆角、按钮、输入、表格、导航、菜单、弹窗、状态与空状态资源；同时已有键盘焦点、DPI 验收和安全文件操作意识。这些内容可以保留并迁移。

问题在于资源与页面之间缺少强制边界：新旧资源字典并行加载，页面仍大量定义局部样式与数值，设计意图无法稳定地穿透到所有模块。

### 0.3 量化现状

对非 DesignSystem 的 XAML 页面做静态统计，当前约有：

| 项目 | 数量 | 风险 |
| --- | ---: | --- |
| 页面级硬编码色值 | 181 | 主题切换、对比度和状态语义漂移 |
| 硬编码字号 | 127 | 层级失控，存在 9、10 DIP 小字 |
| 硬编码 Margin | 1110 | 大量 3、5、6、7、9、10、14、18、28 等非统一节奏 |
| 硬编码 Padding | 157 | 控件触达面积与密度不一致 |
| 显式 Width / Height | 601 | DPI、小窗和长文案下易裁切 |
| 页面内 Style 定义 | 76 | 组件分叉，难以全局修复 |
| Button 实例 | 488 | 操作噪声与“工具面板”感增强 |
| Border 实例 | 299 | 容器和卡片被过度使用 |

`MainWindow.xaml` 与 `AssetLibraryPage.xaml` 分别约 152 KB 与 114 KB，是样式、结构与业务状态高度集中区域。现有字号实际出现 9—38 DIP 共 16 档，而基础规范只定义有限层级；现有视觉资源还同时存在 `Controls.*.xaml` 与旧版 `Buttons.xaml`、`Cards.xaml` 等兼容字典。

### 0.4 当前 UI 问题报告

#### 颜色不统一

- A-v2 语义色之外，素材库局部样式仍维护另一套青绿、蓝灰、白色与半透明色值。
- 设置页允许多个强调色预设，与“全产品只有一个品牌强调色”的要求冲突。
- 品牌金、主青绿、日历五色和状态四色同时出现时，没有明确的面积和层级预算。
- 部分禁用控件仍以高对比白底表现，视觉上比可用内容更强。

结论：颜色已被命名，但还未被治理。后续新增代码只能使用语义 token，品牌 Logo 色不得自动成为控件颜色。

#### 间距不统一

- 基础间距已定义为 4、8、12、16、24、32、48，但页面中大量使用 3、5、6、7、9、10、14、18、20、28。
- 工作台、设置、工具页分别采用 14、24、28 等页面边距，空间节奏切换明显。
- 密集工具区依靠不断缩小 gap 塞入控件，而不是折叠次级信息或改变布局。

结论：4px 基础单位存在，但没有成为约束。

#### 字体层级问题

- 页面中存在 9、10 DIP 文本，长时间观看与高 DPI 可读性不足。
- 18、20、22 DIP 在不同页面同时承担页面标题、区块标题、空状态标题和弹窗标题。
- Metadata、Caption、辅助说明、禁用原因没有稳定区分。
- 字重和颜色经常代替结构，造成“处处像标题、处处又不够重要”。

结论：层级数量过多，语义不足；必须收敛为六个文本角色。

#### 信息密度问题

- 工作台首屏同时出现项目统计、处理任务、日程、最近项目、右栏日历、任务中心和提醒信息，用户无法立刻识别下一项摄影工作。
- 素材库右侧 Inspector 同时展示预览、分析、智能文件夹、色彩检索和批量任务，图片浏览面积被工具控制器持续侵占。
- 大量永久展开的说明、诊断文字和禁用入口使“可做什么”与“未来可能做什么”混在一起。

结论：当前密度主要来自控件和系统状态，而不是摄影内容。

#### 卡片滥用

- 工作台使用多层带边框面板、指标卡、日程卡和右栏卡片组织几乎所有内容。
- `PanelBorder` 被同时用于稳定分组、卡片、提示和空状态，容器角色不清。
- 面板套面板与每块内容都有边框，使画面接近 SaaS Dashboard。

结论：边界替代了排版和留白，形成明显企业后台感。

#### 按钮过多

- 页面中约有 488 个按钮实例；素材库工具栏、Inspector 和 Context Menu 暴露大量低频或禁用动作。
- 多个操作拥有相近视觉权重；“更多”“刷新”“查看全部”“管理”“打开”等频繁占据稳定位置。
- 未实现能力以禁用按钮长期展示，增加噪声且使产品显得未完成。

结论：需要一个主操作、少量上下文操作，其余进入菜单或随选择出现。

#### 图片区域不足

- 工作台几乎没有近期摄影作品或项目封面，摄影身份只靠图标和文案表达。
- 素材库虽以缩略图为中心，但顶部筛选、左侧分类、右侧 Inspector 与底部状态共同压缩画布。
- Inspector 是信息面板而非 Viewer，缺少沉浸大图、缩放、平移和前后浏览。
- 灵感托盘目前以抽屉能力存在，尚未形成“一叠参考照片”的视觉体验。

结论：产品拥有图片数据，但界面仍优先展示管理控件。

#### 企业后台感

- 工作台采用“项目概览 + 指标数字 + 任务中心 + 表格式日程”的典型 Dashboard 结构。
- 项目历史、摄影收支等页面以 DataGrid 和操作列为主，缺少项目封面、时间叙事和摄影语境。
- 顶部原生菜单、左侧分组导航、密集右栏与底部状态栏叠加，形成多层管理软件框架。

结论：功能结构合理，但视觉语言更像数据库管理工具，不像摄影工作空间。

#### 廉价感来源

- 小字号、窄控件、细碎边框、过密按钮和多种局部色值同时出现；
- 白色输入块与暗色背景反差过强，像未完成主题适配；
- 禁用控件仍占据大量空间，暴露实现边界；
- 统一线性图标之外仍存在符号、文字箭头和诊断文案混用；
- 页面大量空黑区域却没有形成有意的负空间，而像内容未加载；
- 缺少图片级 Loading、Preview 与精细 Hover，摄影内容没有“被珍视”的感觉。

廉价感并非来自深色主题本身，而来自缺少取舍：每个功能都在争夺固定位置、边框和按钮。

### 0.5 审查判断

当前 UI 基础可用、主题资源较完整，也已有一部分正确的暗房方向；但整体仍处于“设计系统资源已建立、产品体验尚未服从系统”的阶段。本阶段只立法，不做视觉整改。

## 01 Design Philosophy

### 1.1 产品定位

Pixel Tart 是摄影师的数字暗房：一个用于观看、挑选、组织、策划、拍摄和交付影像的私人工作空间。

它的空间隐喻来自摄影工作室、暗房、档案馆、编辑桌和画廊。用户打开软件的第一感受应是：

> 这是我的摄影工作空间。

Pixel Tart 不是企业管理系统、ERP、数据后台、AI 工具面板或素材下载站。业务数据存在的目的，是帮助用户继续摄影工作；数据本身不占据舞台中心。

### 1.2 Image First

所有页面遵循：

> 图片 > 空间 > 信息 > 控件

- 图片是主体，不是装饰或卡片封面。
- 空间用于观看、比较和思考，不用于填满更多控件。
- 信息只在能够帮助判断时出现。
- 控件在需要时出现，不能持续压缩图片。
- 禁止为了多显示一行文字、一个统计数字或一个筛选器牺牲图片观看面积。

没有图片的页面也要遵循同一原则：把“正在做的摄影工作”放在数据汇总之前。

### 1.3 Calm Interface

界面必须安静、克制、可长时间停留：

- 一个视域最多一个 Primary；
- 不使用大面积彩色按钮、强渐变、发光与高饱和背景；
- Badge 只用于短暂、必要、可解释的状态；
- 不把每块内容包装成 Card；
- 动画只解释空间与状态变化；
- Hover 的变化应被感知，但不应抢走照片注意力。

### 1.4 Professional Photography Tool

专业感来自精确、可靠和尊重作品：

- 颜色中性，避免影响照片色彩判断；
- 比例、裁切、像素、色彩空间和文件安全信息准确；
- 选择、比较、撤销、恢复与导出行为可预测；
- 操作结果不伪造，不用演示数据装饰空界面；
- 视觉参考摄影书、接触印相、编辑桌和画廊，而非 SaaS 后台。

### 1.5 Content Before Chrome

工具栏、侧栏、状态栏与 Inspector 都属于 Chrome。它们必须让位于内容：

- 可折叠的工具默认可折叠；
- 低频工具进入上下文菜单、命令面板或 Drawer；
- 仅在选中对象后显示与对象有关的操作；
- 内容为空时解释下一步，不保留一个假装有内容的大容器。

### 1.6 Honest States

界面只表达真实能力和真实状态：未实现能力不以长期禁用按钮冒充；加载、空、离线、部分完成、失败与完成必须互相区分；任何可能改变源文件的动作必须明确影响范围并提供恢复路径。

## 02 全局视觉原则

1. **暗色优先，中性校色。** Dark 是主要创作环境，背景不得偏色到影响图片判断；Light 和 High Contrast 保持相同信息结构。
2. **一层一个重点。** 页面、Drawer、Dialog 各自最多一个主动作；嵌套容器不得复制主动作。
3. **留白建立层级。** 优先用 8—24 DIP 间距、对齐和字号建立关系，最后才使用边框。
4. **照片不服从卡片比例。** 图片保持原始比例，只有明确的项目封面或用户主动选择的裁切才允许填充裁切。
5. **状态不污染作品。** 状态色位于文字、图标、细边框或画布外区域，不覆盖大面积图片。
6. **桌面效率不等于密集。** 快捷键、右键、拖拽和批量选择承担效率，不靠永久堆放按钮。
7. **DPI 是设计输入。** 使用 DIP、内容驱动尺寸与可折叠区域；不通过缩小文字解决空间不足。
8. **可访问性不是另一个主题。** 键盘、焦点、对比度、非颜色通道与 Reduced Motion 属于默认组件契约。

## 03 全局结构

### 3.1 4px 间距系统

所有空间值以 4 DIP 为基础单位。合法原子值只有 4、8、12、16、24、32、48；组件不得自由发明 3、5、6、7、9、10、14、18、20、28 等视觉间距。

| Token | 值 | 固定用途 |
| --- | ---: | --- |
| `Space.1` | 4 | 图标与短标签、紧密 Metadata |
| `Space.2` | 8 | 同组控件、紧凑图片间距 |
| `Space.3` | 12 | 标准 Gallery / Card 间距、字段内部 |
| `Space.4` | 16 | Panel 内边距、控件组之间 |
| `Space.6` | 24 | 标准页面边距、Section 之间 |
| `Space.8` | 32 | 大区块分隔、沉浸内容边距 |
| `Space.12` | 48 | 页面章节与空状态外部空间 |

语义映射：

| 场景 | 默认 | 紧凑 / 小窗 | 展示 / 大屏 |
| --- | ---: | ---: | ---: |
| 页面水平边距 | 24 | 16 | 32 |
| 页面垂直边距 | 24 | 16 | 32 |
| 稳定 Panel 内边距 | 16 | 12 | 24 |
| 项目 / 任务 Card 内边距 | 16 | 12 | 16 |
| Card 之间 | 12 | 8 | 16 |
| Gallery 图片之间 | 12 | 8 | 16 / 24 |
| 同组控件之间 | 8 | 4 | 8 |
| 控件组之间 | 16 | 12 | 24 |
| Section 之间 | 24 | 16 | 32 |

“紧凑”是布局模式，不是任意减 1—2 DIP。页面只能选择预定义模式，不能逐处调整。

### 3.2 尺寸与圆角

| Token | 值 | 用途 |
| --- | ---: | --- |
| `Size.Control` | 38 | 标准输入与按钮高度 |
| `Size.Control.Compact` | 32 | 工具栏与 Inspector |
| `Size.Row` | 最小 42 | 列表行，内容可撑高 |
| `Radius.Small` | 4 | 小型标记 |
| `Radius.Control` | 6 | 输入与按钮 |
| `Radius.Card` | 8 | 项目、图片、任务卡 |
| `Radius.Drawer` | 10 | Drawer |
| `Radius.Dialog` | 12 | Dialog |

禁止手机式大圆角、无语义胶囊和用圆角数量制造层级。

### 3.3 Workspace Layout

```text
┌─────────────────────────────────────────────┐
│ Top Bar：位置、全局命令、任务与窗口状态      │
├──────────┬──────────────────────┬───────────┤
│ Nav      │ Canvas / Content     │ Info      │
│ 导航分类 │ 图片与当前工作主体     │ 上下文信息  │
│          │                      │ 可折叠      │
└──────────┴──────────────────────┴───────────┘
```

- 左侧：导航、集合或分类；稳定但可收起。
- 中间：视觉主体；始终获得剩余空间和首要滚动权。
- 右侧：当前选择、参数或说明；没有上下文时收起，不展示永久空壳。
- Top Bar：不重复页面导航，不承载页面内所有功能。

详细布局见 `06_Page_Design_Principles.md`。

### 3.4 层级

| 层级 | 名称 | 用途 |
| --- | --- | --- |
| L0 | App | 应用背景、窗口壳层 |
| L1 | Workspace | 长时间工作的页面与画布 |
| L2 | Local Panel | Inspector、局部编辑、筛选与辅助面板 |
| L3 | Floating | Menu、Tooltip、Toast、Drawer、Dialog |
| L4 | Immersive | 大图 Preview、客户监看与演示模式 |

不能用“更亮的 Card”无限制造新层级。

## 04 设计系统目录与唯一来源

未来组件资产按以下目录治理：

```text
Design System
├─ Design Tokens
│  ├─ Color
│  ├─ Typography
│  ├─ Spacing / Size / Radius
│  ├─ Motion
│  └─ Elevation / Overlay
├─ Components
│  ├─ Controls
│  ├─ Navigation
│  ├─ Feedback
│  ├─ Image
│  └─ Floating Surfaces
├─ Patterns
│  ├─ Loading / Empty / Error / Success
│  ├─ Selection / Bulk Actions
│  ├─ Import / Export / Undo
│  └─ Search / Filter / Sort
├─ Layouts
│  ├─ Workspace
│  ├─ Gallery
│  ├─ Preview
│  └─ Planning Canvas
└─ Pages
   └─ 每个模块只组合上列资源
```

工程规则：

- 新页面必须引用 Design Token 和共享组件；
- 禁止在页面中新增硬编码颜色、字号、圆角、阴影或任意间距；
- 禁止为单页复制共享控件 Style，禁止单独写局部 CSS / XAML 样式绕过系统；
- 允许的例外必须先记录语义、范围、期限和替代方案；
- 旧资源键只作为迁移别名，不能成为新页面 API；
- 设计系统变更先更新规范与组件，再更新页面。

## 06 本阶段不修改项

本阶段不做以下工作：

- 不大规模调整现有页面结构或视觉；
- 不重构 `MainWindow.xaml` 或各模块业务代码；
- 不改变功能逻辑、任务状态机、数据库或文件操作；
- 不新增一级导航；
- 不启用尚未实现的 Viewer、情绪板、策划中心或外部应用能力；
- 不更改当前主题资源值或 Accent 设置；
- 不加入新动画；
- 不覆盖当前工作树中其他开发者的未提交改动。

本次输出只建立设计宪法和未来 Review 门禁。

## 07 治理与版本

- Design System 使用独立版本号；破坏现有视觉语义的变更升级主版本。
- 新增 token 前先证明无法由现有语义表达；“页面看起来不一样”不是新增 token 的理由。
- 每个新组件必须有 Default、Hover、Pressed、Focused、Disabled；选择组件还要有 Selected；异步组件还要有 Loading、Empty、Error 和 Success。
- 每个页面 PR 必须附 `07_UI_Review_Checklist.md` 结果和目标 DPI 截图。
- 设计债务以“硬编码、局部 Style、重复组件、越权状态色、缺失状态”五类登记，不以个人审美描述。
