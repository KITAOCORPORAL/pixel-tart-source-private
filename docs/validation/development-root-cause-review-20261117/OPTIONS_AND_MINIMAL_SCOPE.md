## 先尝试推翻B

1. 保存后还有后台变更：禁用输入不足以冻结文档。必须按捕获document/revision复核；保存r1后生成r2不能凭“已保存”释放r2。
2. provider忽略取消：token只表达请求。发布epoch门必须独立；登记Task必须真正等待，不能清空列表或强制GC伪装drain。
3. 多个Closing参与者：只修画布而让主窗口/暗室/联机各自再Close，仍能覆盖取消或nested pump。必须有唯一最终关闭决定，未纳入参与者仍是缺口。
4. 临时切页与多持有者：Unloaded不能等同最终释放；FrozenBitmap仍可能供导出、比较和撤销使用。不能清全局缓存或dispose另一工作区master。
5. 释放期失败：文件可能已持久、部分资源已释放，不能简单复位Open。需要Faulted、失败阶段和可恢复文件入口，不自动丢内容或强杀。
6. 跨root自动回收：正确关闭协议也挡不住外部Kill。链接生产源码的自有子进程已复现；所有权恢复必须单独解决，不能靠改进程名或拉长超时规避。
7. 新版本与重试不是同一操作：不能用WorkflowProjectId独自去重所有后续交付。应明确请求种类、相册/选择版本和目标编辑版本，多相册业务须先对齐。
8. 大范围不自动更安全：现有SQLite aggregate事务、工作文件跨进程锁+指纹、HTTP确认校验和缓存所有权补丁各有职责，不应删除或统一成一个Busy标志。

这些反例要求B明确边界，并未证明需要C的全局迁移。B不是多个模块数据库的分布式原子提交；某文档已保存而后续模块取消，不要求回滚已正确保存的文件。
