# 三种方案与最小修复建议（尚未实施）

## 方案比较

|维度|A 局部遏制|B 单次关闭协议 + 画布生命周期（推荐）|C 全模块资源会话化|
|---|---|---|---|
|做法|在原Closing/Unloaded上追加检查、排队、清图像|根窗口独占关闭意图；现有模块作为异步准备参与者；画布明确停用/终止、跟踪任务与发布epoch|将暗室/联机/画布/选片/缓存/导出统一进新Session与资源租约框架|
|正确性|能处理部分晚到结果；多个取消决定和nested pump仍分散|能够建立可验证的单次尝试、失败和终止边界；依赖所有关闭参与者接入|理论覆盖最广，但正确性取决于迁移完整性|
|跨模块影响|低；状态分歧留在现有边界|MainWindow与画布5文件，Host已有await/重试契约继续用|高；跨导出、撤销历史、临时输出、SDK与共享预算|
|释放时机|往往混淆Unloaded和终止，过早或过迟|暂时停用停止新工作，保留受预算缓存；终止时禁止发布→取消→drain→释放自身持有引用|由所有租约计数决定，必须完整迁移旧所有者|
|数据丢失风险|取消被重发覆盖、共享缓冲提前释放、保存失败已清空|准备失败保留可编辑对象；释放期失败进入Faulted，不能假装恢复可编辑|迁移中最高；双重dispose、失效快照或错删发布中间文件|
|二阶/三阶影响|更多布尔守卫；新模块接手容易再补偿|关闭可能等待慢provider；需超时反馈、显式取消及复原策略，但不强杀/丢弃|调用链与调试成本初期陡增，旧数据/版本兼容范围大|
|维护成本|初期低、长期高|中等，职责和诊断入口清楚|最高，需专门迁移与可回退工程|

A不能把DispatcherPriority换成“更低”当作离开Closing的证明；嵌套消息循环仍可执行排队项。也不能在异常后catch并无界重试Close，掩盖取消或形成循环。A仅适合作为有明确退役条件的临时隔离措施，本轮不建议实施。

B借鉴事务的准备/提交边界和结构化并发的父作用域等待子任务。这里是每个文档的持久保存与一次关闭意图协调，**不是多个模块数据库的分布式原子提交**；某文档在后续取消前已保存不必回滚，用户修改仍保留。与C相比，不迁移像素所有权/预算服务，不创建通用大框架。

## 先推翻推荐B

1. 保存r1后，后台回调写入r2，再按“已保存”释放：仍会丢r2。需要停止新变更入口、对实际document/revision复核；只禁用窗口输入不足以阻止后台提交。
2. provider忽略token：取消并不等于完成。epoch/终止状态发布门必须独立于token；任务仍由会话跟踪并await，慢任务不能用清空Task列表伪装drain。
3. 暂时切到另一个工作区，随后返回：把Unloaded等同Dispose会永久断订阅或丢预览；必须区分Suspend/Resume与TerminalRelease。
4. 一个FrozenBitmap同时被导出、编辑器、撤销/重做或比较视图持有：Freeze保证不可变，不意味着无其他所有者。只能释放本作用域的引用/租约，不能清全局缓存或dispose另一工作区的master。
5. 根窗口仍挂有独立Closing处理器：它可取消/开模态pump，重新引出C1/C2。B必须移除画布独立Close链，盘点所有根窗口参与者；第三方额外处理器未纳入时，不能宣称协议完整。
6. 准备成功后drain失败：保存文件已持久，但会话可能部分释放，不能把状态复位Open后让用户继续操作失效对象。需显式Faulted/失败阶段与可恢复文件入口；不强制GC或自动丢弃。
7. 外部实例恢复按进程名误杀另一个root：产品Codex的独立回执已证明此条件性路径。即使B正确也不能挡住外部Kill；根级所有权核对必须由对应修复单独解决，不通过增加关闭超时或改进程名绕过。

这些反例没有迫使采用全局C；它们要求B的局部协议足够明确，并把跨root恢复作为另一独立前置风险。若审核无法承诺根窗口单一关闭入口，B不能缩成“新增一个Task字段”后直接落地。

## 拟改最小范围

以下是待审接口/契约，不是已经应用或编译验证的补丁。

|现有文件|最小职责变化|

AssetLibraryWorkspaceHost现有await页面释放与lease顺序不先改。App.OnExit的同步Shutdown必须在根窗口drain后只遇到已完成的任务；如果实测仍启动新Dispatcher工作，则需要扩大范围，回审App/模块关闭协议，不能在UI线程新增同步阻塞等待。

不在本方案改动像素公式、RAW解码、导出编码、WorkflowProjectId、发布中间文件协议、全局预算算法或用户UI布局。资源所有权重命名先限本次触及路径，不全库批量改名。

## 建议状态和所有权

关闭状态仅用Open→Preparing→Releasing→Closed；准备取消/失败返回Open，释放期失败为Faulted。每次尝试绑定窗口/root、AttemptId、捕获的文档及revision和在途Task；不再用可跨尝试残留的flushed布尔量代替保存凭证。

画布显示作用域用Active/Suspended/Released及epoch：Suspended允许受预算的已有缓存，但不启动新工作或接纳旧结果；Released不可恢复，资源由父作用域等待并收回。不要把保存gate、可见性、任务取消和图像租约混成一个“忙碌”标志。

## 审核后实施的验收门禁

- 在最终修复源码上重跑本15项：C1无重入、C2取消保持打开、C3目标改变有显式结果、I1/I3不晚到发布、I2停用不新增工作。重复请求共享同一完成结果。
- 扩充最强反例：保存期间第二次编辑、后台变更、慢/忽略取消provider、准备失败恢复、终止阶段故障、共享图像仍在导出、关闭后不可重新排队。
- 保存、撤销/重做、真正独立进程重开、导出参数/像素/ICC与现有基线比较；当前夹具存储重开不是此项的替代。
- 使用独立合成工程，再接已有授权输入。自然50ms内存采样，无强制GC；核对拥有者数量及稳定预算，不强制要求OS立即decommit。
- 保留用户原运行根、未保存备份、现有40MP/RAW批次授权和2GiB守卫。不得为“退出成功”自动丢弃或误杀另一root。

审核问题只有一个：是否接受B的上述5文件最小范围及门禁？本轮停止在建议，未实施产品修改。
