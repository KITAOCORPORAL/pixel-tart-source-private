# 像素蛋挞测试与发布规范

## 1. 当前审计结论

- 当前真实版本：2.0.3；
- 最新有效自动化结果：405/405 通过；
- 测试源码约 377 个 TestMethod，其余数量来自数据驱动用例；
- 当前安装包 SHA-256：`D6768A5DDC8A3CBCD5AA9C9FB21675006252A7FE480DA9BEF1A9AC60FD8F1AA9`；
- 当前工程没有 Git；
- 当前发布脚本使用共享 `artifacts/publish/win-x64`，不满足未来不可变发布要求。

## 2. Git 和版本规则

进入下一开发阶段时：

1. 初始化本地 Git，默认分支 `main`；
2. 首次提交前确认 `.gitignore` 排除 bin、obj、发布物、日志、用户配置、密钥和照片；
3. 将当前 2.0.3 冻结为基线提交并创建 Tag `v2.0.3`；
4. 每个版本使用 `release/2.0.4` 等独立分支；
5. 版本发布后合并 main 并创建签名或注释 Tag；
6. 不修改已发布 Tag，不覆盖同名安装包；
7. 建立 CHANGELOG.md。

本轮不初始化 Git，因为当前最高优先级只允许审计和文档；该动作是下一阶段的第一个门禁任务。

## 3. 版本一致性

以下必须一致：

- Directory.Build.props Version；
- Branding.ProductVersion；
- WPF csproj Version/FileVersion/AssemblyVersion；
- app.manifest；
- Inno Setup AppVersion 和文件名；
- About/设置可见版本；
- 发布目录 manifest；
- 安装后文件版本。

构建脚本在不一致时必须失败。

## 4. 版本化目录

```text
artifacts/releases/<version>/publish/win-x64/
artifacts/releases/<version>/installer/
artifacts/tests/<version>/
artifacts/ui-review/<version>/
artifacts/install-verification/<version>/
```

每个版本生成 `release-manifest.json`：

```json
{
  "status": "released",
  "releaseEligible": true,
  "version": "2.0.4",
  "sourceCommit": "...",
  "sourceCommitMeaning": "binary-source-commit",
  "sourceTag": "v2.0.4",
  "releaseTag": "v2.0.4",
  "releaseTagTarget": "...",
  "builtAtUtc": "...",
  "configuration": "Release",
  "runtime": "win-x64",
  "selfContained": true,
  "testTotal": 0,
  "testPassed": 0,
  "installerBytes": 0,
  "installerSha256": "...",
  "licenseProvider": "None",
  "signed": false
}
```

### 4.1 源码提交、文档提交与 Tag 语义

1. 产品源码提交可以早于最终文档或发布元数据提交。
2. `sourceCommit` 始终表示生成当前二进制和安装包的产品源码提交，`sourceCommitMeaning` 使用 `binary-source-commit`。
3. `releaseTagTarget` 表示发布 Tag 在审计时解析到的提交；Tag 目标可以包含发布报告和 manifest。
4. 不要求 manifest 在自身内容中记录“包含该 manifest 的提交哈希”，避免形成不可满足的自引用提交哈希。
5. `documentationCommit` 可选，用于记录后续纯文档或元数据修正提交；二进制身份由 `sourceCommit` 与 `installerSha256` 共同确定。
6. 纯文档或发布元数据修正不要求重新构建安装包。
7. 只有产品代码、依赖、资源或构建配置发生变化时，才必须重新构建、重新测试并生成新的二进制哈希。
8. 已推送到远端或已被外部发布记录引用的 Tag 不得移动、删除或强制覆盖。
9. 仅存在于本地、没有远端副本且没有外部发布引用的错误 Tag，可以在完成远端与发布记录审计后重建一次；重建后不得再次移动。

## 5. 每版构建顺序

1. 工作区状态审计；
2. `dotnet clean`；
3. `dotnet restore`；
4. Debug Build；
5. Release Build；
6. 单元测试；
7. 集成和文件安全测试；
8. WPF UI 结构测试；
9. 实际启动与视觉验收；
10. `win-x64 self-contained` 发布；
11. 生成新版本安装包；
12. 计算大小和 SHA-256；
13. 隔离安装、启动、核心流程、重启、卸载；
14. 生成报告和 release manifest；
15. 创建 Tag；
16. 停止，等待用户确认。

## 6. 测试分层

### 单元测试

解析、标准化、分组规则、冲突策略、路径约束、模板布局、数据库迁移纯逻辑。

### 文件系统集成测试

使用每个测试独立临时目录。覆盖：中文、空格、超长路径、只读、权限、磁盘不足模拟、占用、断盘、损坏文件、零字节、同名、取消和部分失败。

### 任务恢复测试

任务执行到不同检查点后模拟退出，验证重启后的 Interrupted、继续、重试和回滚。验证幂等性和不会重复覆盖。

### UI 结构与真实 UI

静态 XAML 测试只检查资源和结构；真实 UI 自动化检查点击、键盘、Popup、拖拽、焦点、无障碍、DPI 和主题。两者不能互相替代。

### 安装测试

全新安装、覆盖升级、旧数据迁移、降级阻止、无控制台、快捷方式、卸载保留数据、选择删除数据。

## 8. 文件安全通过标准

- 不覆盖未授权目标；
- 不删除源文件；
- 取消后无未知部分输出；
- 断盘/空间不足有明确错误；
- 操作清单与实际一致；
- 恢复不会重复执行已完成文件；
- 撤销前置条件失败时停止；
- 报告能追溯每个文件。

## 9. 发布阻断条件

- 任何测试失败；
- 版本字段不一致；
- Release 启用 Mock；
- Provider 配置与报告不一致；
- 文件操作存在静默覆盖/删除；
- 没有安装包 SHA-256；
- 安装、启动或卸载失败；
- UI 有阻断级重叠、裁切或白底控件；
- 数据迁移没有备份；
- 发布目录覆盖旧版本；
- 当前源码没有可追溯 Git 提交。

## 10. 回传报告

每版报告必须列出完成/未完成、数据模型、文件清单、测试、安装、大小、SHA-256、迁移、已知问题、下一版本依赖和是否建议进入下一阶段。报告数据必须从当前命令和产物获取，不复制旧报告数字。

## 11. 工作日历发布门禁

- 月/周/日、时区、跨天、夏令时和结束早于开始的校验必须覆盖；
- 重叠排期、延期项目、同项目重复创建和“仍然保存”必须有测试；
- 文档丢失、重新定位、移除关联不删除原文件必须有隔离文件系统测试；
- 金额字段隐藏、待收计算、隐私日志脱敏和诊断包脱敏必须有测试；
- 提醒默认关闭，只有用户主动启用才可请求系统通知；
- SQLite 迁移、备份、失败回滚和旧版本只读保护未通过时，不得发布 2.2.0。
